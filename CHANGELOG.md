# Changelog
- Phase Q build 0.1.46 implements Gate 15 Q2 after the 0.1.45 article spike physically proved a title-only Reader revision leaves local progress/highlights/notes intact and normalized visible text unchanged. Normal Sync now examines up to 5 pending HTML articles per cycle with bounded read-only Reader HTML GETs. If the pending Reader revision exactly matches the fetched revision and visible text is unchanged, only the durable refresh-pending marker is cleared; local document bytes and sidecar are untouched. Changed/unverified HTML, revision races and raw PDF/EPUB revisions remain pending. Automatic content replacement stays disabled.\n- 0.1.45 fixes the first physical Gate 15 crash from 0.1.44. KOReader `ffiUtil.copyFile` returns `nil` on success; the v1→v2 DB backup code had interpreted that success as failure and raised from the menu callback before migration. Backup semantics are corrected and regression-tested against the real KOReader contract. The Gate 15 diagnostic also removes unnecessary `ffi/sha2` hashing in favor of direct normalized-string equality, and parent-process DB/sidecar preflight exceptions are contained so they show a safe message instead of escaping the callback. Existing local content replacement remains disabled.\n- Phase Q diagnostic 0.1.44 starts Gate 15. Database schema v2 persists a remote-revision/content-refresh-pending state separately from metadata `remote_updated_at`, new materializations record the remote revision they actually contain, and Sync never overwrites an existing local document. A read-only **Inspect content refresh safety (Gate 15)** action compares article visible text remotely vs locally under bounded reads and reports KOReader sidecar/progress/annotation risk signals. Raw PDF/EPUB revisions are always deferred in this build. No content replacement is authorized yet.\n- Phase P build 0.1.43 implements Gate 14 Finished → Archive after the 0.1.42 PW3 spike physically proved `doc_settings.summary.status == "complete"` as the canonical Finished signal. Archive intent is durably queued before remote reachability, Reader state is GET-reconciled before every PATCH/retry, `location=archive` is idempotently PATCHed, local DB/Readwise Collection location is updated without deleting or rewriting the local file/sidecar, and unchanged second syncs do not re-PATCH a known archive. The setting **Finished documents → Archive in Reader** defaults ON per the V1 plan.\n- Phase P diagnostic 0.1.42 starts Gate 14 without assuming KOReader finished semantics. KOReader v2026.07.1 source shows Finished maps to `summary.status = "complete"`; the new local-only diagnostic compares the persisted sidecar summary, BookList status and current runtime summary for the managed document. It performs no network request and no local write. Archive PATCH implementation remains blocked until the PW3 confirms the persisted signal experimentally.\n- Phase O diagnostic 0.1.41 follows the physical 0.1.40 parent-fetch pass. The reconnect hard-exit boundary is now text matching. Annotation matching no longer calls KOReader native `ffi/utf8proc.normalize_NFC`; its conservative Unicode fallback uses pure-Lua Latin base+combining composition, while exact/whitespace/punctuation matching remains unchanged. The read-only Gate 13 diagnostic now executes the real matcher with durable per-stage breadcrumbs (`visible_text`, `exact`, `unicode`, `whitespace`, `punctuation`) and still performs no remote writes.\n- Phase O diagnostic 0.1.40 follows the 0.1.39 physical hard exit at `parent_reads`. It removes text matching from the reconnect probe, splits each parent check into metadata-only and bounded HTML fetch stages, caps Reader parent LIST bodies at 1 MiB for this diagnostic, and persists sanitized partial snapshots after every stage so queue/marker evidence survives even if the child process exits. Normal Sync mutation remains frozen and unchanged.\n- Phase O diagnostic 0.1.39 follows the physical Gate 13C reconnect failure. It adds a read-only reconnect probe that snapshots create-queue status without mutation, runs the auth probe in the same subprocess model as Sync, scans Reader highlights for exact KOReader ownership markers, verifies parent-document text matching without POST/PATCH/DELETE, and persists only a coarse local stage name so a hard child-process exit still leaves a useful diagnostic. Normal Sync behavior is not relaxed and no blind retry is introduced.\n- Phase O hotfix 0.1.38 addresses the physical 0.1.37 Gate 13A worker failure by isolating real-device sidecar scan/queue exceptions per managed document, falling back safely if the optimized local-document query fails, isolating malformed annotation normalization within a sidecar, and surfacing the worker failure stage instead of only “Document sync failed safely”. No remote-write authorization was weakened; the read-only Readwise auth probe remains mandatory before queue processing or mutations.\n- Phase O 0.1.37 closes the Phase L/N staging gap by discovering new create-highlight work across every locally-present Reader-managed document on manual Sync, with the currently open document prioritized. Discovery remains local-only before the read-only Readwise reachability probe; missing/non-authoritative sidecars are skipped safely, remote-only documents are not loaded into the scan, and note/delete mutations remain bounded to the current document.\n- Phase O hotfix 0.1.36 stops treating KOReader/Kindle local network flags as authorization for remote writes. The target PW3 returned unavailable native Airplane Mode properties while KOReader still reported Wi-Fi/connected/online=true with no internet. Sync now queues the current local annotation first, then performs the existing read-only Readwise auth GET inside the cancellable worker; only a successful probe permits queue processing, annotation mutations, or document sync. Probe failure preserves the durable queue and does not advance the document watermark.
- Phase O diagnostic 0.1.35 adds a read-only Gate 13 network-state inspector after 0.1.34 also failed to detect the target PW3's effective online state correctly. It reports raw Kindle `airplaneMode`, `wirelessEnable`, `wifid enable`, KOReader Wi-Fi/connected/online state, and the plugin's derived decision. The diagnostic performs no Readwise requests or writes.
- Phase O hotfix 0.1.34 makes Kindle Airplane Mode authoritative for offline queueing. KOReader 2026.07.1 `NetworkMgr:isOnline()` only checks DNS reachability and the Kindle backend can restore Wi-Fi independently, so build 0.1.33 could still run the online path after the user enabled Airplane Mode. 0.1.34 reads the native `com.lab126.cmd airplaneMode` flag on Kindle, refreshes radio/connectivity state, and forces ordinary Sync now into local-queue-only mode whenever Airplane Mode is active.
- Phase O experimental 0.1.33 hardens outbound annotation creation for offline/reboot/retry scenarios. Ordinary Sync now can queue local annotations with Wi-Fi off; durable create intents survive restart; retryable preflight failures use `retry_wait`/`available_after`; 429/auth can retry only after safe reconciliation; timeout/5xx/stale in-flight outcomes are never blindly re-POSTed; and queue processing can resume independently of the original in-memory document session.
- Phase N hotfix 0.1.32 replaces unreliable Reader `source/saved_using` as the destructive delete authority with stronger cross-API identity: exact durable Reader child id + expected parent/category + exact Readwise v2 highlight whose `external_id` equals that Reader child id. DELETE success is not persisted until the Reader child is confirmed gone.
- Phase N hotfix 0.1.31 makes note update success end-to-end: after a Readwise v2 PATCH, the plugin polls the linked Reader v3 child before advancing the durable baseline. If v2 already has the desired note but Reader is stale, it performs a verified Reader v3 repair PATCH. This also repairs the premature-success state created by 0.1.30.
- Phase N hotfix 0.1.30 fixes false note conflicts caused by invisible representation differences between KOReader sidecars and Readwise (CRLF/LF and surrounding/trailing whitespace). Normalization is used only for comparison; the exact local note text remains the payload written to Readwise.
- Phase N hotfix 0.1.29 moves production note conflict detection/update to the deterministic Readwise v2 representation already proven in Gate 8: Reader child id is matched exactly to v2 `external_id`, the current remote note is read from v2, and note PATCH uses that exact v2 highlight. Reader v3 remains the parent/child identity check; remote deletion remains unchanged and strict.
- Phase N hotfix 0.1.28 fixes the remaining Gate 12 note-update blocker observed on the target PW3. Reader may return a linked highlight child without the expected saved_using/source marker even though its durable child ID, original parent ID and highlight category all match. Non-destructive note updates now accept that durable identity and can retry an item previously left blocked by the 0.1.27 identity check. Remote DELETE remains strict and still requires the exact per-annotation ownership marker.
- Phase N hotfix 0.1.27 fixes a Gate 12 regression for highlights created by pre-Gate-10 builds. Those older linked Reader children used the generic `saved_using = "KOReader Readwise Reader"`; note updates now accept that legacy ownership marker only when durable child ID + parent ID + highlight category also match. Destructive DELETE remains restricted to the newer exact per-annotation marker.
- Phase N experimental 0.1.26 adds linked highlight-note updates during **Sync now**, with three-way conflict detection against the last-synced note. If local and Reader notes both diverged, the plugin records a conflict and overwrites neither side.
- Highlight deletion propagation is now available under **Settings → Highlights**, remains OFF by default, requires an explicit destructive-action confirmation, and deletes only a durable linked Reader child whose id, parent, category and KOReader source marker all match. Local deletion with propagation OFF leaves Reader unchanged.
- Phase L experimental 0.1.25 connects current-document KOReader highlights to normal **Sync now** using Reader v3 parent-linked creation, literal note transport, durable remote child IDs, and a SQLite create queue.
- Highlight create uses a stable per-annotation `saved_using` marker. A timeout/crash or any previously-attempted create is blocked and reconciled by exact Reader `source` + parent identity before any retry; the plugin never blindly repeats an ambiguous POST. Gate 10 remains pending physical validation.

Matching now operates on Reader-visible text rather than raw HTML, decodes common/numeric entities, ignores non-visible script/style/comment content, handles inline-tag splits, Unicode NFC, whitespace/NBSP, soft hyphens and conservative straight/curly quote + dash equivalence, and rejects repeated ambiguous matches.

## [1.1.0] - 2026-09-25

### Added

- Historical Reader → KOReader import uses a pre-Sync reconciliation so an existing remote highlight is resolved before any local create can POST a duplicate back to Reader.
- Adds SQLite schema v3 global remote-highlight cache: historical Reader v3 baseline, incremental `updatedAfter`, a 5-minute overlap, cache semantic versioning, and Readwise v2 `EXPORT includeDeleted=true` tombstones keyed by exact external IDs.
- Unsafe exact-position/note conflicts and ambiguous equivalent-text candidates suppress outbound creates for that run rather than guessing identity. Suppressed durable queue items remain unattempted.
- Adds bounded/starvation-safe batches (20 new annotations / 30 locator attempts), native KOReader sidecar persistence verification, durable child-ID linking, and per-item rollback.
- Hardens v2→v3 migration rollback by checkpointing WAL before the automatic pre-migration `readwisereader.sqlite3.bak` copy; deterministic tests cover v1/v2 migration, v3 rollback, cache replacement, tombstones, pagination and restart-safe queue semantics.
- v1.1.0 scope is rolling EPUB/HTML historical import. PDF/paging historical import is explicitly deferred to Gate 17D rather than extrapolated from CRengine rolling-document XPointers.

### Development history

- Experimental `1.1.0-alpha.3` adds bounded/idempotent historical Reader → KOReader highlight batches for the currently-open managed rolling EPUB/HTML and integrates them after successful manual `Sync now`. Each run creates at most 20 annotations / attempts at most 30 locators, preserves Reader notes, skips already-linked IDs and unsafe locator/collision cases, and keeps the proven sidecar-verification + durable-link rollback contract. A cancelled/failed post-Sync import is reported separately and does not invalidate an already-completed document Sync.
- Experimental `1.1.0-alpha.2` Gate 17B imports exactly one pre-existing Reader highlight into the currently-open managed EPUB/HTML after unique XPointer validation, verifies sidecar persistence, preserves Reader notes, and durably links the existing Reader child ID so a later outbound scan cannot treat it as a new remote create. - Experimental `1.1.0-alpha.1` Gate 17A: read-only Reader → KOReader historical-highlight locator probe for open managed EPUB/HTML documents. It scans Reader highlight children by exact parent ID and tests up to three passages against KOReader rolling-document search/XPointer APIs. No local or remote annotation is written yet.
