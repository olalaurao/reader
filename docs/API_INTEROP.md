# Annotation API interoperability — Gate 8

Date: 2026-09-23  
Target client: KOReader v2026.07.1 / Kindle PW3  
Plugin branch: `phase-j/annotation-api-gate8`

This file is the required evidence ledger for the Phase J hard gate. It separates current public API contracts from behavior that still must be demonstrated against the user's real Reader/Readwise account.

No production annotation update/delete behavior may be enabled merely from the documented contract below. Gate 8 closes only after the staged disposable test records the actual cross-API behavior.

## Current documented contracts

Sources reviewed on 2026-09-23:

- Reader API: https://readwise.io/reader_api
- Readwise API: https://readwise.io/api_deets
- Readwise changelog/docs as supporting context only.

### Reader v3 highlight create

Document CREATE is `POST /api/v3/save/`.

When `parent_id` is supplied:
- the request creates a highlight child;
- `content` is required and must match the passage as it reads in the parent's Reader content;
- `notes` is the note attached to the new highlight;
- `tags` is accepted;
- documented success is 201, or 200 when the document already exists;
- response shape contains the new Reader document `id` and `url`.

Sanitized spike request shape:

```json
{
  "parent_id": "<disposable-reader-parent-id>",
  "category": "highlight",
  "content": "Gate Eight exact highlight phrase for KOReader interoperability testing.",
  "notes": "gate8 initial [[Foucault]]",
  "tags": ["koreader-gate8"],
  "saved_using": "KOReader Readwise Reader"
}
```

Expected sanitized success shape:

```json
{
  "id": "<reader-highlight-child-id>",
  "url": "<reader-url>"
}
```

### Reader v3 highlight LIST representation

Reader Document LIST now documents that:
- highlights and notes are Documents with `parent_id`;
- on a highlight, `notes` carries the attached note;
- `highlight_offset` is the character offset in the parent's plain text;
- `highlight_location` is the serialized DOM start/end pair.

The Gate 8 spike records whether those fields are actually populated for the disposable HTML parent.

### Reader v3 highlight update — contract changed from the original project assumption

The current Reader Document UPDATE documentation explicitly says that **on a highlight, `notes` and `tags` are accepted** and other fields return 400.

Therefore the spike now tests Reader v3 PATCH before falling back to Readwise v2 for note updates:

```http
PATCH /api/v3/update/<reader-highlight-child-id>/
```

Sanitized body:

```json
{
  "notes": "gate8 updated through Reader v3 [[Foucault]]",
  "tags": ["koreader-gate8", "gate8-v3-updated"]
}
```

This supersedes the older assumption in the spec that a highlight note could not be updated through v3. Production architecture will follow the observed Gate 8 result, not the old assumption.

### Reader v3 delete

Document DELETE is:

```http
DELETE /api/v3/delete/<reader-highlight-child-id>/
```

Documented success is 204. Reader documents that deleting a highlight also deletes its attached note.

### Readwise v2 representation and mapping candidates

Readwise v2 Highlight LIST/DETAIL expose:
- numeric `id`;
- `text`;
- `note`;
- `book_id`;
- `external_id`;
- `updated`;
- tags/color/location fields.

The Readwise Export API documents a stronger Reader-source bridge:
- a Reader-backed user book has `source = "reader"`;
- the user-book `external_id` identifies the Reader source document;
- each exported highlight also has an `external_id`.

Gate 8 therefore first tests the simplest deterministic hypothesis:

```text
v2 highlight.external_id == Reader v3 highlight child id
```

If that fails, it tests the Export API shape:

```text
v2 user_book.external_id == Reader parent id
AND
v2 highlight.external_id == Reader highlight child id
```

A match based only on parent + text + note is recorded as **non-deterministic** and blocks production v2 mapping rather than being silently accepted.

### Readwise v2 update/delete

Documented endpoints:

```http
PATCH  /api/v2/highlights/<numeric-id>/
DELETE /api/v2/highlights/<numeric-id>/
```

PATCH supports at least `note` and `color`. The disposable spike uses:
- note: `gate8 updated through Readwise v2 [[Foucault]]`
- color: `green`

It then queries Reader v3 again to determine whether the v2 note mutation propagates back to the same Reader highlight child.

## Automated spike implementation

Build 0.1.22 uses only disposable data generated by the plugin.

Stage 1:
1. create a temporary Reader article with supplied HTML;
2. wait until Reader LIST returns its HTML with the exact test phrase;
3. create one child highlight through Reader v3;
4. verify v3 parent/category/note/tag and locator fields.

Stage 2:
1. query recent Readwise v2 highlights;
2. require a deterministic `external_id` mapping, with Export API as a documented fallback probe;
3. persist the numeric v2 ID only after deterministic mapping;
4. PATCH the highlight note/tags through Reader v3;
5. verify through Reader v3 LIST.

Stage 3:
1. PATCH that exact mapped numeric v2 highlight;
2. set note + green color;
3. verify the response;
4. poll Reader v3 to see whether the note appears there.

Stage 4:
1. DELETE the child through Reader v3;
2. verify Reader v3 no longer lists it;
3. probe the exact mapped v2 ID;
4. if v2 still exposes the disposable highlight, record that fact and use v2 DELETE only for this already-proven disposable ID;
5. DELETE the disposable parent;
6. clear local Gate 8 state only after cleanup succeeds.

A separate recovery action can clean only the Gate 8 IDs stored by this spike after cancellation/failure.

## Architecture decision after Gate 8

Pending observed evidence.

Possible outcomes:
- if Reader v3 create/update/delete is reliable and the v3 child ID maps deterministically to v2, prefer v3 for Reader-native mutations and use v2 only where it adds a proven capability;
- if v3 note update is reliable, the production note-edit path no longer needs v2 solely for note mutation;
- if v3 delete reliably removes the corresponding Readwise highlight, production deletion can stay on v3 (still opt-in/default OFF);
- if any mapping or propagation is ambiguous, the relevant edit/delete capability remains disabled rather than guessed.
